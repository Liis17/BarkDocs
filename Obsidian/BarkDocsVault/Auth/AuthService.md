# AuthService

Parent: [[Index]]

## Назначение

Сервис `barkdocs-auth`: аккаунты [[Admin/AdminConsole|веб-консоли]], их сессии и API-ключи агентов. Ключ имеет вид `bd_` и 64 hex-символов, токен сессии — `bds_` и 64 hex-символов; в БД хранятся только их SHA-256. Пароли хранятся как argon2id. Мастер-ключ берётся из `ADMIN_KEY`, сравнивается по хешу и в БД не записывается.

## Источники

| Файл | Значимый символ | Роль |
|------|-----------------|------|
| `backend/barkdocs-auth/src/main.rs` | `router`, `main` | Маршруты, запуск, создание администратора |
| `backend/barkdocs-auth/src/principal.rs` | `Principal` | Кто управляет: мастер-ключ или сессия консоли |
| `backend/barkdocs-auth/src/keys.rs` | `verify` | Проверка ключа агента, возвращает роль, владельца и id ключа |
| `backend/barkdocs-auth/src/keys.rs` | `create_key`, `list_keys`, `revoke_key`, `visible_owner` | Ключи: свои — пользователю, любые — администратору |
| `backend/barkdocs-auth/src/users.rs` | `register`, `login`, `logout`, `me`, `change_password` | Аккаунты и сессии |
| `backend/barkdocs-auth/src/users.rs` | `list_users`, `get_user`, `update_user`, `bootstrap_admin` | Управление пользователями |
| `backend/barkdocs-auth/src/crypto.rs` | `hash_token`, `generate_token`, `hash_password`, `verify_password` | Хеши, генерация токенов, argon2 вне async-потоков |
| `backend/barkdocs-auth/migrations/` | `api_keys`, `users`, `sessions` | Схема `auth` |

## Публичные контракты

Адрес по умолчанию `0.0.0.0:8081`, переопределяется `BIND_ADDR`.

| Контракт | Поведение и условия |
|----------|---------------------|
| `POST /verify` (Bearer-ключ) | 200 с `{role, user_id, key_id}`: мастер-ключ — `admin` без владельца, ключ агента — всегда `user`. 401, если ключ неизвестен, отозван или его владелец заблокирован |
| `POST /register` (`{login, password}`) | 201 с пользователем; 403 при `ALLOW_REGISTRATION=false`; 409, если логин занят или совпадает с `ADMIN_LOGIN` |
| `POST /sessions` (`{login, password}`) | 201 с `{token, user}`; 401 — неверные данные; 403 — заблокирован; 429 — 10 неудач подряд за 15 минут |
| `DELETE /sessions`, `GET /me`, `POST /me/password` | Выход, текущий пользователь, смена пароля (завершает остальные сессии) |
| `POST /keys` (`{name, user_id?}`) | 201 с ключом, показывается один раз. Владелец — текущий пользователь; другому пользователю выдаёт только admin. Не больше 100 активных ключей на пользователя |
| `GET /keys?user_id=&all=` | Пользователь — только свои ключи; admin — свои, конкретного пользователя или все; мастер-ключ по умолчанию — все |
| `DELETE /keys/{id}` | 204. Пользователь отзывает только свои ключи; иначе или при повторном отзыве — 404 |
| `GET /users`, `GET /users/{id}`, `PATCH /users/{id}` (admin) | Пользователи с числом активных ключей; блокировка (`disabled`) и роль. Себя заблокировать или понизить нельзя |
| `GET /healthz` | `ok` |

## Зависимости и взаимодействия

- Вызывается [[Web/Gateway|Публичным шлюзом]] через `POST /verify` при каждом запросе.
- Вызывается [[Admin/AdminConsole|веб-консолью]] с токеном сессии для всего остального.
- Управляющие маршруты принимают мастер-ключ или токен сессии; ключ агента там не действует.
- Использует собственную схему `auth` в PostgreSQL; миграции применяются при старте.

## Ограничения и важные детали

- Сервис не стартует без `ADMIN_KEY` длиной не менее 32 символов.
- При заданном `ADMIN_PASSWORD` на каждом старте создаётся или обновляется администратор `ADMIN_LOGIN` (по умолчанию `admin`): пароль и роль перезаписываются, так забытый пароль восстанавливается перезапуском.
- Отзыв мягкий: строка остаётся, заполняется `revoked_at`. Ключи без владельца (созданные мастер-ключом) продолжают работать.
- Блокировка удаляет сессии пользователя; его ключи перестают проходить `/verify`, но не отзываются и снова работают после разблокировки.
- `last_used_at` ключа обновляется в фоне не чаще раза в минуту.
- Счётчик неудачных входов хранится в памяти и сбрасывается перезапуском. Пароль несуществующего логина сверяется с фиктивным хешем, чтобы время ответа не выдавало логин.
- В `docker-compose.yml` порт открыт только на `127.0.0.1`, поэтому управление ключами доступно с хоста.

## Решения и основания

- Хранится только хеш ключа. Основание: комментарий в `main.rs` — «В БД хранится только sha256 ключа, сам ключ показывается один раз при создании».
- Admin-ключ не хранится в БД. Основание не задокументировано; в коде указано только сравнение с хешем из окружения.
- Ключи агентов не получают роль владельца. Основание: комментарий у `verify` — утечка ключа агента не должна давать права на изменение индекса.
